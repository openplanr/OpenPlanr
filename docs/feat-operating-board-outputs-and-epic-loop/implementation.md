### T-006 reachability completion (round 2, dispatched after the round-1 QA gate)

Per the task file's own "Plan amendment (orchestrator, post QA gate 2026-08-01)"
section, a scoped completion closed the reachability gap **without adding a new CLI
command** — the plan amendment explicitly preferred automatic election on acceptance
over inventing a new surface, and that is what shipped.

**Built:** `governOperatingFinding` (`lifecycle.ts:426-523`) now calls
`electAcceptedFindingEpicRoutes({ projectRoot, localRoot, cycleId })` unconditionally
after accepting a finding and auto-accepting that finding's own individually-proposed
route — the pre-existing idiom, unchanged. `electAcceptedFindingEpicRoutes`
(`routes.ts:719-824`, new) re-reads the committed event log, recomputes
`groupRelatedAcceptedFindings` (T-006's round-1 grouping, reused unmodified) over the
cycle's currently-accepted findings, filters out any candidate group already headed by
a committed `create-epic` route (`existingEpicRouteFindingIds`, anchor-keyed), and for
each newly-eligible 2+-member group: builds the route via `createOperatingRoutePlan`
(round-1, unmodified), writes it through the journal (`commitProposedRoute`, new), and
appends `route.proposed` then immediately `route.accepted` (`appendRouteEvent`, new) —
mirroring exactly how governance already auto-accepts a finding's own individual route,
just applied to the epic group.

**Reachable production path, traced end to end:**
`planr operate findings accept <id1>` → `planr operate findings accept <id2>`
(completes a 2+-member themed group; a `create-epic` route is proposed **and**
accepted automatically in the same call) → `planr operate routes apply <ACT-id>`
(existing, unmodified, generic CLI verb) →
`.planr/epics/EPIC-NNN-<slug>.md` is written with every member finding ID in the body
→ `planr operate routes rollback <ACT-id>` byte-exact reverses it. `src/cli/commands/operate.ts`
has zero diff for this completion — no new CLI surface was needed.

**Accept ≠ apply preserved:** `commitProposedRoute` writes only the route plan record
(`.planr/operate/routes/{route.id}.json`) through the journal — never the epic
markdown itself. The epic body is only ever built inside `buildRouteWrites`, which
election reaches only in-memory (to compute `previewDigest`, no disk write); the real
write happens only from an explicit `applyOperatingRoute` call with a matching digest.

**Idempotence, confirmed by a dedicated test:** accept finding 1 (no group yet) →
accept finding 2 (elects exactly 1 epic route) → accept finding 3 (grows the group to 3
members; asserts 0 *new* epic routes and the same previously-elected route id) →
calling `electAcceptedFindingEpicRoutes` again directly also returns `[]`.

**Drift-on-growth, empirically probed, not just traced:** QA built a throwaway test
(`tests/integration/operate-tmp-epic-drift-check.test.ts`, deleted immediately after
running — confirmed via `git status --porcelain` showing zero trace) that accepted
finding A, then B (electing a route over `{A,B}`), then accepted C **before** applying
the still-`{A,B}`-digest route. The apply call threw
`error.code === 'E_OPERATE_ROUTE_DRIFT'`; no partial or stale epic file was written.
Ruled acceptable, fail-safe behavior inherited from the same digest-drift mechanism
already proven for every other route kind — not a defect.

**Documentation inaccuracy found during the completion (non-blocking, comment-only,
not fixed in this pass):** `electAcceptedFindingEpicRoutes`'s own doc-comment
(`routes.ts:696-717`) claims a grown group "still writes `{A,B,C}`" at apply time. The
traced and empirically-probed behavior is that apply **fails** with
`E_OPERATE_ROUTE_DRIFT` in that scenario — it does not write the grown set. The comment
describes what `resolveEpicGroupForAnchor` *computes*, not what the apply path actually
*does* with a digest mismatch. Flagged as a follow-up; see [`drift.md`](./drift.md).

**Follow-up opened (real, not yet built):** no `routes` CLI verb or action lets an
operator re-propose or refresh a drifted epic route. Because
`existingEpicRouteFindingIds` is keyed off *any* historical `route.proposed` event for
the anchor — not "successfully applied" — a route that drifted and failed apply
permanently blocks that anchor from ever heading a fresh `create-epic` proposal, even
as the underlying group keeps growing. More likely to bite in practice for epics
specifically, since accepting related findings incrementally is an expected operator
flow.
