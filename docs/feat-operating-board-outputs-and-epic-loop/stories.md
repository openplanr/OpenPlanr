## US-001 — planr-pipeline 0.35.0 mission-budget and epic-route contracts

**As** the planr-pipeline package every OpenPlanr Operating Board consumer depends on,
**I want** `maxEvidenceItems` enforced as a loud, reported truncation inside
mission-packet construction, the operating-roles registry budgets reviewed against real
index-item costs, and the v1.3 `operating-route-plan` schema to accept an additive
`create-epic` action kind, **so that** OpenPlanr's engine can truncate an oversized
mission evidence index safely and route grouped findings to a governed epic-creation
action, both as a real, versioned contract the dependent engine tasks pin.

Acceptance outcome: an over-limit `evidenceIndex` is truncated to exactly
`maxEvidenceItems` entries with `budgets.truncatedEvidenceItems === true`; an index at
or under the cap is untouched with the flag absent or false; a route-plan document with
`actions[0].kind: "create-epic"` validates against
`schemas/v1.3.0/operating-route-plan.schema.json` while an existing `create-quick-task`
document still validates unmodified; every registry role publishes reviewed budgets and
an explicit `dispatchMode`; `planr-pipeline@0.35.0` is published to npm with tag
`v0.35.0`. Grounds FR4's pipeline half and FR8's schema half. No dependencies — the
external-publish precondition US-004 and US-006 pin via `dependsOn: ["T-001"]`.

## US-002 — Truthful cycle outputs and legacy tree consolidation

**As** a decision owner reviewing a governed Operating Board cycle, **I want** the
complete lens report and role board content persisted as real files — not
900-word-capped or `enabledRoles`-derived stubs — the legacy `projections/` directory
retired, and `backlog.md` promoted to the top-level readable tree, **so that** the file
tree is never a broken pointer to intelligence that only exists transiently in
`review`/`report` output, and there is exactly one authoritative readable copy of every
register.

Acceptance outcome: `cycles/<id>/report.md` exists once a cycle reaches
`reviewable`/`closed` and equals `readOperatingReport({cycleId}).markdown`, exempt from
the 900-word brief cap; an evaluated role's `board/<role>.md` renders the same
recommendations, I/C/E scores, and evidence references as
`planr operate report <cycleId> --lens <role>`; a role with no advisor-result record
states plainly it was not evaluated, and Status derives from that absence, not from
`config.enabledRoles`; every report hint reads
`planr operate report <cycleId> --lens <role>`; `.planr/operate/projections/{register,
decisions,data-gaps}.md` and `projections/state.json` no longer exist, and
`.planr/operate/backlog.md` exists at the top level. Grounds FR1 (the spec's named
centerpiece) and FR6. No dependencies.

## US-003 — Evidence integrity: no silent loss, prioritized fair collection

**As** the decision owner relying on Operating Board evidence, **I want** every filter
that drops evidence to report what and how much it removed, sensitivity narrowing
scoped to only the offending items, and a capped monorepo walk that samples `apps/`,
`packages/`, and `infra/` fairly instead of dying alphabetically on dotfiles, **so
that** a role never dispatches "ready" on an empty evidence base, and a real
repository's product code is never starved out by planning trees consuming the whole
cap first.

Acceptance outcome: the mission index's dot-prefixed path-pattern drop count appears in
the evidence bundle's warnings; a `maxFiles` truncation names the last path reached and
the top-level directories never scanned; sensitivity narrowing removes only the
above-ceiling item, leaving compliant siblings under the same root reachable; a role
whose post-index evidence retains zero repository items is excluded from dispatch with
a governed evidence gap while other ready roles still dispatch; a capped monorepo walk
represents all three product directories in the collected items. Grounds FR2 and FR3.
No dependencies.

## US-005 — Re-initialization preserves machine-local preferences

**As** an operator re-running `operate init` on an already-initialized project, **I
want** `dispatchModeOverrides`, `adapterLeaseDurationMs`, and `lastRunAt` carried

to prior behavior. Grounds FR5. No dependency on US-001/T-001 — a purely local

## US-006 — Epic loop: grouped-finding suggestion and route-kind closure

**As** the decision owner reviewing a cycle's accepted findings, **I want** related
findings grouped into one ready-to-run epic suggestion, and a governed `create-epic`
route that actually writes the epic and threads provenance forward, **so that** the
operating loop closes: finding → epic → spec → plan/ship becomes traceable end to end,
without ever auto-invoking PLAN or SHIP.

Acceptance outcome: two or more accepted findings sharing a category or Chair
merge-lineage produce one `planr epic create --title …` suggestion in the report's
exact-next-actions naming both; a route-plan document with `actions[0].kind:
"create-epic"` validates against the published v1.3 schema; applying an accepted
create-epic route writes `.planr/epics/EPIC-NNN-<slug>.md` through the CLI's epic seam
with every member finding ID recorded in the document; apply then rollback restores the
working tree byte-exact; no `create-epic` route in any state ever triggers a PLAN or
SHIP invocation. Grounds FR7 and FR8's engine half. Depends on US-001/T-001 — a
`create-epic` route only validates against the published v1.3 schema once 0.35.0 ships
the additive enum value. Per `clarifications.md`, the shared v1.3 route-plan schema
keeps a single `findingId` per action; this story's task records the full
member-finding list only in the OpenPlanr-local epic document, not a new
protocol-schema-governed sidecar — resolved as Option A (recommended, adopted). Round-1
QA adjudicated a genuine reachability gap against this story's own intent (the route
was buildable but not reachable from any operator-facing surface); a scoped completion,
dispatched after the round-1 gate, closed it — see `implementation.md`.
