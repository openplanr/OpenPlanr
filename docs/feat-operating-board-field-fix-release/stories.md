## US-001 — planr-pipeline 0.34.0 mission-dispatch contracts

**As** the planr-pipeline package every OpenPlanr Operating Board consumer depends on,
**I want** the v1.3 record action to name the generated lens agent, the guided-question
schema to carry an additive `preselected` field, the operating-roles registry published
at protocolVersion 1.3.0 with an explicit per-role `dispatchMode`, and the adapters
registry modernized (the native-capable adapter's dispatch capability renamed to
`"native-read-only"`, the other adapters confirmed/renamed to `"structured-provider"`),
**so that** OpenPlanr's engine has a real, versioned contract to dispatch a mission
packet to a named subagent instead of a generic pack pointer.

Acceptance outcome: a v1.3 mission-mode record action carries `dispatch.agent ===
"operating-<roleId>"` alongside the existing fields; a v1.2 guided-question document
with no `preselected` field still validates, and a new document with `"preselected":
true` also validates; the operating-roles registry loads at protocolVersion 1.3.0 with
every role carrying an explicit `dispatchMode`; the adapters registry loads at
protocolVersion 1.3.0 with the native-capable adapter's
`capabilities.operatingAdvisorDispatch === "native-read-only"` and the
structured-provider-routed adapters' `capabilities.operatingAdvisorDispatch ===
"structured-provider"`; `commands/operate.md` and the generated skill template document
the mission branch and the interim exit-4-is-handoff rule; `planr-pipeline@0.34.0` is
published to npm with tag `v0.34.0`. Grounds FR1's pipeline half and FR9's schema
field. No dependencies — the external-publish precondition US-003 and US-007 pin.

## US-002 — Enforce pack input budgets

**As** the Operating Board dispatch pipeline, **I want** `createOperatingAdvisorPack` to
measure the canonicalized pack against the role's `budgets.maxInputBytes` and fail
closed at both the dispatch and adapter-prepare call sites, **so that** a multi-megabyte
pack — like the real 2,736,185-byte pack the field run shipped against a 384 KB registry
contract — can never reach a provider or adapter.

Acceptance outcome: a role whose canonicalized pack would exceed `budgets.maxInputBytes`
throws a typed, budget-naming error mirroring `E_OPERATE_MISSION_PACKET_BUDGET`'s
fail-closed semantics, and nothing is sent to any provider or adapter from either call
site; an in-budget pack still dispatches exactly as before; the stale
`advisors.ts:481` docstring no longer claims pack mode already enforces the budget; the
existing mission-packet budget path continues to pass unmodified. Grounds FR2, called
out in the spec as an "independent stopgap." No dependency on US-003 — shares
`advisors.ts` with no genuine output dependency (advisory file overlap only, per the
current native-dispatch model).

## US-003 — Wire mission dispatch for real

`protocolVersion: '1.3.0'` to reach both adapter-handoff call sites, `adapter record` to
accept v1.3 citation-bearing responses for mission roles, and `--dispatch-mode-override`
to be execution-effective, **so that** a mission packet — not a pack — actually reaches
the record action on a native-capable runtime, closing the gap where the six generated
lens agents were registered but dispatched by nothing.

Acceptance outcome: roles resolving to mission dispatch mode store a real
`buildOperatingMissionPackets` output at `/data/missionPackets/<role>`, not a rolePack;
`protocolVersion: '1.3.0'` reaches `protocol.createOperatingAdapterHandoff` from both

new end-to-end test proves the exact mission packet (not a pack) is what a
native-capable test harness submits through; a mission-mode role's citations flow into
`gateRecordedProposalCitations` exactly as the structured-provider path already does;
`--dispatch-mode-override` forcing a role to `"pack"` actually dispatches via the pack
path, not merely labels provenance; `provenance.dispatchMode` never reads `"mission"`
for a role that was actually packed; a v1.2 project with no role moved to mission mode
behaves exactly as before. Grounds FR1, the release's centerpiece. Depends on US-001
(T-001) — the mission branch's exact contract shape (`dispatch.agent` naming, explicit
per-role `dispatchMode`, the adapters-registry capability rename) is defined there and
this story's end-to-end test asserts against that published shape.

## US-004 — Human surfaces render text, continuation is not failure, action contracts are executable

**As** an operator running `planr operate` from a terminal or automation harness,
**I want** `operate review` to render human-readable Markdown instead of raw JSON,
guided-stage and first-use-consent continuations to return an `ok:true` (`flow:
"handoff"`) shape instead of a bare failure, and every structured action's command
string to be directly executable, **so that** a healthy continuation never paints the
happy path red, the review gate is actually readable without `--json`, and no runner
has to hand-reconstruct a stripped command.

Acceptance outcome: `operate review` without `--json` renders Markdown/readable-tree
content (the same brief/lens-report assembly `readOperatingReport` already produces),
never `JSON.stringify(result.data)`; `--json` returns the exact raw state object
unchanged; a guided-stage advance and first-use provider consent both report `ok:true`
with a `flow: "handoff"` discriminator; `publicActionCommands` no longer strips a
confirmation token the runner must re-synthesize (or a separate `confirmArgv` is
provided), and no `confirmationDigest` attaches to a command (like `run`) that accepts
no `--confirm` flag; the confirmation flag vocabulary is unified across init/run/routes.
Grounds FR3, FR7, and FR8 — grouped because all three resolve inside the same
`success()`/`failure()`/`renderHuman` response-shaping code, and splitting them would
create three tasks racing the same functions with no genuine output dependency. No
declared dependency — `index.ts` edits sit adjacent to US-006's runtime-detection edit
in the same region (advisory file overlap only).

## US-005 — Bind machine-local state to board identity and diagnose it correctly

**As** an operator running successive Operating Board generations against the same
repository, **I want** adapter sessions and the incremental evidence cache to carry the
board's identity, the evidence cache to honor its own already-written `workspaceDigest`,
a committed init apply to purge stale machine-local caches, a finalized adapter session
to check expiry/binding instead of forcing whole-cycle cancellation, and the doctor
command to diagnose exactly these two staleness conditions with scoped repair commands,
**so that** a new board generation never collides with a prior one's machine-local
state, and never reports a misleading `E_OPERATE_STATE_INVALID` with no path forward.

Acceptance outcome: two successive board generations never collide on adapter-session
identity; a `workspaceDigest` mismatch causes the evidence cache to recollect deep
instead of trusting stale evidence; a committed `operate init` apply purges
`<localRoot>/advisors/` and `<localRoot>/evidence/incremental/`; a finalized or expired
adapter session is superseded, not fatally cancelled, for a new compatible prepare;
`planr operate doctor` reports two new named diagnostics with scoped fix commands
without disturbing any pre-existing diagnostic; post-upgrade lock-drift presents as
expected-after-upgrade, not a FAIL implying Operating Board breakage. Grounds FR4 and
FR11 — one story because FR11's two new diagnostics are direct detectors for exactly the
two staleness conditions FR4 fixes. No dependency on US-001/US-003 — entirely
OpenPlanr-side, consumes no pipeline-published contract.

## US-006 — Eliminate the masked first-run crash and detect the real runtime

**As** an operator running the first `operate run` inside an unconfigured or
unrecognized environment, **I want** provider bootstrap failures to surface as a typed,
actionable error instead of a generic internal error, a preflight key check before a
cycle starts, and the guided/JSON init path to actually probe runtime identity instead
of stamping `unknown`/`none`, **so that** the exact crash the field run hit cannot recur.

Acceptance outcome: a provider bootstrap failure surfaces as a typed
`E_OPERATE_ADVISOR_FAILED` preserving the actionable remedy, never
`E_OPERATE_INTERNAL`; any error resolving to `E_OPERATE_INTERNAL` carries a redacted
error class/name; `operate run --preview` (or a readiness check) names a missing key
before a cycle starts; the JSON init path probes environment markers specific to each
supported host environment and/or the existing binary probe instead of stamping
`{"runtime":"unknown","interaction":"none"}`; a persisted `"auto"` preference resolves
to the detected host and never silently disables native dispatch; the runtime question
becomes detect-don't-ask. Grounds FR5 and FR6 — grouped because they are the two links
in the exact crash chain the audit reproduced ("adapter stamped unknown/none → auto
persisted → native dispatch disabled → provider path → unguarded key error"). No
declared dependency, though `usesNativeOperatingAdvisors`'s edit aligns with US-001
(T-001)'s adapters-registry rename to `"native-read-only"` (coordination note, not a
blocking output dependency).

## US-007 — Questionnaire integrity and diet

**As** an operator running `operate init` for the first time, **I want** the write-only
`timezone` question removed, `cadence`/`component-roots` demoted out of the required
first-run batch, `planning-engine`/`decision-owner`/`sources` corrected and honestly
probed, charter deferral defaults restored, per-choice `preselected` carried
schema-to-UI, and `--answers-file` added as a bounded stdin-parity alias, **so that**
the first-run questionnaire asks only what actually blocks progress, never traps on an
unconfigurable source, and never fabricates availability or options.

Acceptance outcome: no `timezone` question exists; a first-run session with only
`decisionOwner`/`planningEngine`/`sensitivityCeiling`/`sources` answered reaches
`preview-ready`, not `input-required`, even with `cadence`/`component-roots`
unanswered; `github`/`linear` are removed or gated from the sources choice list until
configurable in-flow, and suggested availability reflects only real, probed capability;
`planning-engine` suggests `"pipeline-po"` when planr-pipeline is installed;
`decisionOwner` is suggested from the detected git user on the JSON/native init path,
mirroring the terminal path's existing behavior; `business-model`/`ideal-customer`
default to "Not yet specified", `known-unknowns` is optional, `product-stage` becomes a
select, `guardrails` is seeded with suggested standing boundaries; a `preselected`
choice renders pre-checked and a repeated-text-shaped question is never fabricated into
a select; `--answers-file <path>` parses through the same bounded parser as `--stdin`.
Grounds FR9. Depends on US-001 (T-001) — `preselected` only round-trips schema-to-UI
once the guided-question schema accepts it.

## US-008 — Adapter lease ergonomics

**As** an operator running a long advisory session through the native adapter
lifecycle, **I want** the lease expiry surfaced in prepare/handoff output, refreshed on
each successful record, and configurable, with the recovery semantics documented,
**so that** a session never silently expires mid-cycle with no visibility, and
re-preparing after expiry doesn't lose already-recorded roles.

Acceptance outcome: prepare and any handoff-returning action surface the lease's expiry
and remaining time; a successfully recorded role refreshes the session's `expiresAt`
(extended, not left at its original prepare-time value); an operator-configured lease
duration is honored by `operateAdapterLifecycle` prepare instead of the hardcoded 15
minutes; an expired session with some roles already recorded survives a fresh, matching
prepare by input-digest binding. Grounds FR10. Self-contained to the adapter-lifecycle
lease mechanics in `maintenance.ts`/`config.ts`, no genuine output dependency on any
other FR in this spec.
