Round 1 **failed** this task: the implementation was read directly and judged
structurally sound, and the full suite (107 files/1034 tests default, 21
files/84 tests heavy at that point) was green — but 5 of 8 DoD items had
**zero automated test evidence**. An exhaustive search for every exported

migration-sounding test file, `tests/integration/operate-legacy-import.test.ts`,
covers an unrelated pre-existing `.planr/board` importer, not this module.
Missing coverage: automatic migration on open of a genuine old-layout project,
digest/event preservation via checkpoint revalidation, byte-exact
`operate migrate rollback`, and crash recovery mid-migration.

The retry (`T-001-error-report.md`, "Retry scope") created
`tests/integration/operate-storage-migration.test.ts` (heavy config, 6 tests)
against a genuine old-layout fixture built independently of `migration.ts`
(a real git repo, a real `operate init` + cycle, then down-converted using
only `event-store` field mappings and `canonicalize`). Running this suite
**exposed a genuine data-loss defect**:

> A crash after the journal's `staged-fsynced` transition, with a partially
> promoted `.state/` view, made `detectOperatingStorageLayout` report `v1.3`
> — so `applyStorageLayoutMigration`'s v1.3 branch called
> `removeLegacyLayout` and destroyed the old-layout backup, the only complete
> copy of the records (reproduced: 9/9 records lost).

**Fix**, confined to the `layout === 'v1.3'` branch of
`applyStorageLayoutMigration` (`src/services/operate/migration.ts:156-183`):
reconcile only when an old-layout backup coexists with `.state/` (a healthy
v1.3 project returns immediately, zero blast radius); call
`recoverOperatingTransactions` (imported from `journal.ts`) first to roll back
any non-terminal migration transaction byte-exact; if the event log survived,
the view was committed, so the backup is removed as before; otherwise the
reverted partial `.state/` is discarded and the function recurses once to
re-migrate from the still-intact backup. One import added
(`recoverOperatingTransactions`); no other source changes. QA's round-2
re-audit traced the recursion and confirmed it terminates (at most one
recursive call).

Round 2 **passed**: the new suite passes 6/6 in isolation and as part of the
full heavy-config run; both crash-injection tests (before and after
`staged-fsynced`) genuinely stage the real multi-material journal transaction
and reproduce each residue directly, rather than mocking `migration.ts` or
`journal.ts`. All three hard-preserve suites (`operate-journal-crash`,
`operate-honeytoken-isolation`, `operate-mission-honeytoken-isolation`)
remained pristine throughout.

**Undeclared-but-attributed change:** `src/services/operate/journal.ts` gained
