# Delegated run handoff

`prepareDelegateRun` builds the complete private capsule, verifies an enrolled profile and its effective destination in the source context, creates one detached worktree, rechecks the destination from that exact worktree, and returns a preview. The preview lists selected capsule files, omissions, the sole writable repository, recorded `integrationScopePaths`, worktree dependency readiness, profile, and verified destination. `scopePaths` is required for new CLI prepares and becomes the integration boundary; optional `selectedPaths` only selects dirty files to copy into the worktree. Present the preview before calling `dispatchDelegateRun`. The enrolled destination and original writable scope carry the user's existing authorization through ordinary dispatch, answers, and corrections. If the effective destination or scope changes, prepare a new preview and obtain authorization for that change.

The packaged helper also accepts `node scripts/runner.mjs probe|prepare|dispatch|resume|status|wait|recover|close|cleanup|prune` with one JSON object on standard input and one JSON result on standard output. `probe` with `{}` confirms local execution and lists enrolled choices. A second `probe` with `{ "profile": "claude-local", "repositoryRoot": "/absolute/checkout" }` checks the selected profile's effective destination and, for a local endpoint, whether its selected model is visible and loaded when the backend has a read-only loaded-state API. `ready: false` blocks handoff, including a confirmed unloaded model; `ready: null` means loaded-state or endpoint/model health has not been established. A model confirmed as loaded may still fail at inference. Load a confirmed unloaded local model through its normal UI and retry the same probe; this helper does not load it automatically. `{ "hostCapabilities": { "localExecution": false } }` returns `E_DELEGATE_HOST_UNSUPPORTED` without reading task context or creating run state. Use standard input for task text and answers so they do not appear in a process argument list. For example, `prepare` takes the same options as `prepareDelegateRun`; `dispatch` takes `{ "runId": "..." }`; `status` reads a run by ID; `wait` accepts a run ID and a timeout of at most 60 seconds; `resume` adds one `answer` or `correction`. A retained run in a nondefault directory can be inspected with explicit `runDirectory`. Operational command output omits the saved answer, capsule bytes, and raw model output. This is a private skill helper, not a public `planr` CLI command.

The private run directory contains `record.json`, `capsule/capsule.json`, `custody.json`, a decoded `capsule/readable/` context mirror, and a versioned `helper/` copy of the packaged scripts. The bounded record stores stable paths, profile and destination identity, initial Git state, status, the exact backend session ID, an internal SHA-256 of the prepared capsule bytes, and the pinned helper identity. Run-specific actions use the pinned helper paths printed at prepare; current package entry points route to that copy when available. A changed copy blocks execution. A record without a helper copy remains readable and status reports `helperCompatibility: "read-only-record"`; execution requires a new prepared run with a pinned helper. The record does not store source bytes, a full dispatch prompt, environment values, or adapter output logs. Files are private to the local user; do not paste their content into routine logs or an issue report. The capsule itself holds the selected source bytes and must remain outside the repository. `validateDelegateCapsule` checks that the file remains byte-identical and private; the runner checks before and after adapter execution, and integration checks before applying changes. Capsule drift blocks the run or integration while retaining its worktree for inspection.

`dispatchDelegateRun` rechecks profile eligibility and Git custody immediately before sending the capsule pointer and readable context index to the adapter. It passes the canonical private `capsulePath` explicitly to `adapter.run` and `adapter.resume` so a generic wrapper can grant only that capsule read access without parsing prose. Claude runs reserve an exact session ID before launch and verify the returned ID; Codex records its `thread.started` ID as soon as the event arrives. `status` distinguishes reserved, observed, and confirmed session evidence. A generic adapter may only provide its session ID with a terminal result, so an interruption before then can leave exact resume unavailable. Initial and resumed prompts require exactly one JSON object with `status` and `summary`, optional `checks` and `issues`, and `question: { text, options? }` only for a question; the adapter adds the backend session ID. It accepts only structured `completed`, `blocked`, or `question` results with a valid session ID. An invalid result becomes a blocked run with its worktree retained. A delegate-reported blocker is kept in bounded form for recovery. Delegate summaries and checks are claims for review; derive actual changed paths and patches from the worktree.

The default 20-minute run limit is an **idle** limit. Validated Claude and Codex event-stream activity resets it, so a working delegate can continue beyond 20 minutes. The separate absolute safety limit is three times the configured idle timeout, capped at one hour; activity cannot extend it. For example, a two-minute idle timeout has a six-minute absolute limit. Headless Claude runs without Bash access; the orchestrator performs checks, then returns failures for correction. Approval denials do not count as progress, and three denials block the run with its worktree and exact session retained. `status` reports the last recorded activity, its evidence, and both deadlines without exposing event contents. Activity is persisted at most once every five seconds, so the displayed idle deadline can trail live progress briefly. A generic adapter without progress events has only its terminal result as evidence and can still reach the idle limit during a long silent call; enroll a progress-capable wrapper if that matters for the task.

For a material question, answer in the active conversation, then call `resumeDelegateRun({ runId, answer })`. Review findings use `resumeDelegateRun({ runId, correction })`. The runner records the latest handoff in the private record and calls `adapter.resume` with the recorded session ID. It never calls `adapter.run` for a handoff and never substitutes the backend's latest session. If exact resume is unavailable, inspect the blocked record and worktree. A timeout, cancellation, process exit, or malformed result also leaves the capsule, worktree, baseline, and known session ID inspectable. Adapter failures retain only allowlisted codes with fixed messages; raw stdout, stderr, and exception text never enter the record.

After an orchestrator restart, call `recoverDelegateRun`. It marks an interrupted run blocked when its recorded process is gone; it does not silently start another session. A blocked run may be resumed only through its recorded exact session when the backend supports it, or explicitly abandoned after inspection.

`closeRunRecord` accepts only an `integrated` or `abandoned` disposition. Successful helper `apply` immediately closes the exact run as integrated after recording observed paths and independent checks. Repeating `close` with the same disposition is idempotent; a different disposition fails. `status` recovers the same five-field final report, accepted paths, generator outputs, checks, and later source drift without disclosing source bytes. Planning status is report-only, even for an unlinked `.planr` directory. The runner rejects another resume and the integration helper rejects another apply after integration. Explicit `cleanup` removes the managed worktree after an accepted or abandoned disposition. `pruneClosedRunRecords` removes the private record and capsule after 30 days by default only after worktree cleanup. Unresolved questions, blocked runs, completed runs awaiting review, and conflicts are never pruned automatically. Record pruning refuses a retained worktree so custody cannot be orphaned. Pending integration writes must be resolved with the integration helper's explicit `recover` action before abandonment or cleanup.

`status` reports preparation, delegate execution/correction and verification timings separately. Execution duration accumulates across exact-session continuations. Verification shows scratch preparation, builds, generation, checks and source writes with command durations; failed attempts remain in their private evidence files. Total elapsed time freezes at closure. Historical records without timing fields remain readable and do not acquire fabricated measurements.
