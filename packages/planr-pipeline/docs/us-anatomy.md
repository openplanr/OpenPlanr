## The User Story Statement

```
As a [role],
I want to [action],
so that [business outcome].
```

Rules:
- **Role** = a real user type, not "user" generically. Use: "admin", "customer", "team member", "guest", etc.
- **Action** = one specific capability. Not compound actions ("create and manage").
- **Business outcome** = why it matters to the business or user, not a technical outcome.

✅ Good: "As a customer, I want to view my order history, so that I can track past purchases."
❌ Bad: "As a user, I want to use the system."

---

## Scope Boundary Rules

Each US must represent:
- **One coherent user-facing capability** (not a technical layer)
- **Independently valuable** — could ship alone and provide value
- **Appropriately sized** — implementable within one sprint by one developer

Avoid:
- Splitting by technical layer ("Frontend US" + "Backend US" for the same thing → that's what tasks are for)
- Combining two separate user goals into one US
- US so small they describe a single button

---

## Acceptance Criteria Format

```
Given [a specific precondition or system state],
when [the user performs a specific action],
then [the system produces a specific, observable result].
```

Rules:
- Minimum 3 criteria per US
- Each criterion must be independently testable
- Use concrete values where possible ("then the list shows 10 items per page", not "then the list is paginated")
- Include at least one negative/error case criterion

---

## Dependencies Format

```yaml
DependsOn:
  - us-{N-1}: [why — what data or state must exist]
  - feat-{name}: [why — what this US needs from another feature]

Blocks:
  - us-{N+1}: [why — what can't start until this is done]
```

Rules:
- Circular dependencies are forbidden (A depends on B depends on A)
- If depends on a DB table, reference the schema.json table name
- If `none`, explicitly write `none` — don't leave empty

## Task Breakdown Table

Every US must explicitly list its tasks:

```markdown
| Task   | File              | Agent           | Summary              |
|--------|-------------------|-----------------|----------------------|
| task-1 | tasks/task-1.md   | Frontend Agent  | [one line summary]   |
| task-2 | tasks/task-2.md   | Backend Agent   | [one line summary]   |
```

Rules:
- If no PNG: only task-1 row (Tech type, Backend Agent)
- If PNG present: both rows (task-1 UI/Frontend, task-2 Tech/Backend)
- Summary must be distinct per task — not "implement the feature"

## Quality Checklist (used by /openplanr-pipeline:review)

```
✅ User story follows As/I want/So that format
✅ Role is specific (not generic "user")
✅ Action is singular and specific
✅ Scope paragraph explains what's IN and OUT
✅ Minimum 3 acceptance criteria
✅ At least 1 negative/error criterion
✅ All criteria are independently testable
✅ Dependencies explicitly listed (even if "none")
✅ Task breakdown table matches actual task files
✅ US scope does not overlap with adjacent US files
```
