## The QA failure → rework story: T-003 citation module

### What failed (first pass, 2026-07-30T23:39:29Z)

`lib/operate/citation.mjs` originally defined its own private, hand-rolled
JSON Schema constants (`CITATION_SCHEMA`, `RESOLUTION_SCHEMA`, lines 59–141
of the failed version) and validated against those instead of the
canonical, T-001-registered `schemas/v1.3.0/operating-citation*.schema.json`
contracts. The two shapes were structurally incompatible — the module's own
object shape (using a `kind`/`citationKind`-style discriminator) was rejected
by the real registered schema with `unknown property 'kind'` when run
through `assertProtocolArtifact('operating-citation', ...)`. This directly
contradicted T-003's own Technical Spec items 1 and 4, which required
validating through `resolveProtocolSchema('operating-citation', {
protocolVersion: '1.3.0' })` — i.e., the registry, not a private copy.

Why this matters beyond "wrong field names": a citation module that
validates against its own private schema instead of the canonical one can
silently drift from the contract every other module (`operating-advisor-response`,
the adapter handoff, the mission packet) actually enforces. The whole point
of FR3 is that citation resolution is the audit mechanism; an audit
mechanism that checks itself against its own private copy of the rules is
not actually auditing against the shared contract.

### The fix (rework, same day)

The reworked `lib/operate/citation.mjs` defines no local schema constant at
all. Every validation call goes through `assertProtocolArtifact(<kind>, ...,
{ protocolVersion: '1.3.0' })` imported from `lib/protocol/contracts.mjs`:

- `validateOperatingCitation()` → `assertProtocolArtifact('operating-citation', ...)`
- `resolveOperatingCitation()` → `assertProtocolArtifact('operating-citation-resolution', ...)`
- `buildUnresolvableCitationGap()` → `assertProtocolArtifact('operating-data-gap', ...)`

Field names now match the canonical schemas exactly (`repositoryPath`,
`gitRevision`, `planrArtifactId`, `lineRange`, `pinnedRevision`,
`citationKey` for citations; `kind`, `schemaVersion`, `protocolVersion`,
`citationKey`, `outcome`, `evidenceId`, `snapshotDigest`, `reason`, `gapId`
for resolutions), and both schemas are `additionalProperties: false`, so the
module cannot carry anything outside the registered contract.

### Independent re-verification (not a re-read of the diff)

The QA re-audit ran the repro directly against the live module and live
schema rather than re-reading the fix:

```
$ node -e "
  const {validateOperatingCitation} = await import('./lib/operate/citation.mjs');
  const {assertProtocolArtifact} = await import('./lib/protocol/contracts.mjs');
  const citation = {

"

```

As a control, the OLD private-schema shape
(`{kind:'operating-citation', citationKind:'repo-path', ...}`) still fails
against the canonical schema with `unknown property 'kind'` — confirming the
canonical schema itself was never relaxed to make the failure disappear; the
fix is in the module.

### Two reviewer flags audited on the merits (not just re-asked)

- **(a) Sensitivity/classification moved off the resolution envelope.**
  `operating-citation-resolution` is `additionalProperties: false` with a
  closed property set that has no `sensitivity`/`classification` field, so
  the module cannot add one without breaking the schema. Instead, the caller
  may pass `sensitivity`/`classification` inside the `facts` object, and
  because `evidenceId`/`snapshotDigest` are `sha256Jcs({ citation, facts })`
  over the *whole* facts object, any change to declared
  sensitivity/classification changes the snapshot binding — the binding is
  tamper-evident even though those fields never appear on the envelope
  itself. A dedicated test
  (`'declared snapshot sensitivity/classification bind into the resolved
  snapshot digest'`) resolves the same citation twice under two different
  sensitivity/classification pairs and asserts both `snapshotDigest` and
  `evidenceId` differ. Verdict: sound.
- **(b) `buildUnresolvableCitationGap` gained an internal `context`
  parameter not exported from the barrel.** A repo-wide grep confirmed
  exactly two call sites (its own definition and its own test); `lib/pipeline/index.mjs`
  exports only `resolveOperatingCitation`/`validateOperatingCitation` from
  this module. The `context` parameter is therefore not part of any public
  contract the barrel promises. Verdict: non-issue.

## Defect-2: the orchestrator-applied remediation to `operating-records-log-entry`

### What was disclosed (non-blocking, first pass)

`schemas/v1.3.0/operating-records-log-entry.schema.json`'s `finding`,
`data-gap`, `route`, and `migration` `oneOf` branches originally `$ref`'d
**only** the v1.3.0-only content schema for each of those record types
(e.g. `finding` → `operating-finding.schema.json`, the v1.3 file, which
requires a `citations` field that a genuine v1.2 finding record does not
carry). Consequence: a container-only migration of a real SPEC-002 v1.2
finding, data-gap, route, or migration record — moving it from the
directory-per-digest-prefix layout into `records.jsonl` **without upgrading
its content** — could not validate as a v1.3
`operating-records-log-entry`, because the v1.2-shaped `content` object
would fail the v1.3-only `$ref`. This directly conflicted with US-005's own
design intent: the migration changes only the record *container*, never the
record *content*.

### The fix (orchestrator-applied, same remediation pass as T-003's rework)

Each of the four affected branches now declares:

```json
"content": {
  "anyOf": [
    { "$ref": "https://openplanr.dev/schemas/v1.2.0/operating-<kind>.schema.json" },
    { "$ref": "operating-<kind>.schema.json" }
  ]
}
```

i.e. a v1.2.0-absolute-URL ref **or** a v1.3.0-relative ref — a genuine v1.2
record validates unchanged, and a genuine v1.3 record (with `citations`,
etc.) also validates. The other seven branches
(`evidence-metadata`, `advisor-result`, `decision`, `spec-link`, `outcome`,
`artifact-manifest`, `recovery`) were left as single-`$ref` v1.2.0 branches
unchanged, because those record types have no v1.3-only content schema to
reconcile against.

`conformance/verify-operating-records-migration.mjs` was extended to assert
that every produced `records.jsonl` line validates as
`operating-records-log-entry@1.3.0` via `assertProtocolArtifact`, in
addition to the pre-existing byte-exactness/losslessness/reversibility
checks.

### Independent re-verification

QA ran `migrateRecordsDirectoryToJsonl()` directly (not through the
conformance script) against the genuine v1.2 fixture
`conformance/fixtures/operating-board/legacy-directory-layout-sample/records/fi/nding-sample.json`
(outer `protocolVersion: "1.2.0"`, embedded `content.protocolVersion:
"1.2.0"`), inspected the produced log-entry line to confirm
`content.protocolVersion` remained `"1.2.0"` (proving the migration really
is container-only), and confirmed
`assertProtocolArtifact('operating-records-log-entry', <produced line>,
{protocolVersion:'1.3.0'})` did not throw. `node
conformance/verify-operating-records-migration.mjs` standalone → exit 0.
**Defect-2 is closed.**

## Drift this document flags beyond what QA already disclosed

The two "JUSTIFIED" deviations above (T-002/`registry/adapters.json`,
T-004/`registry/operating-roles.json`) were reviewed and accepted by QA, but
they are still genuine gaps between the acceptance-criteria text and what is
on disk, worth restating plainly for anyone reading the code without the
QA report in hand:

- **US-002 AC:** "`registry/adapters.json`'s three existing adapters ... each
  declare a v1.3-compatible dispatch classification." **Actual:**
  `registry/adapters.json` has no v1.3 fields at all —
  `adapterEnforcesBoundedReadOnly()` in `lib/operate/adapter-handoff.mjs`
  derives the v1.3 boundedness from the pre-existing v1.2
  `capabilities.toolIsolation === 'enforced'` field instead. Functionally
  equivalent today (only `claude-code` has `toolIsolation: 'enforced'`, and
  that is the adapter the spec wants classified `native-read-only`), but a
  reader of `registry/adapters.json` alone will not see any v1.3
  classification because none was written.
- **US-004 AC:** "`registry/operating-roles.json`'s six role IDs are
  unchanged; each role gains a `dispatchMode: 'pack' | 'mission'` field."
  **Actual:** the field is not present in `registry/operating-roles.json` on
  disk; `lensRolesInOrder()` in `scripts/generate-operating-assets.mjs`
  defaults every role to `'mission'` in memory at generation time. There is
  currently no on-disk mechanism to mark a role `'pack'` for the migration
  coexistence FR10 describes — doing so today would require changing the
  generator's default, not editing the registry.

Both were disclosed in `.planr/specs/SPEC-004-operating-board-agentic-execution/qa-report.md`
as Deviations #3 and #4 and disposed "JUSTIFIED, intent satisfied," and both
are consistent with every automated gate above (they cannot be caught by
schema validation, since the v1.3 role-registry and adapter-registry schemas
are only exercised against in-memory derived views in the v1.3 conformance
script, never against the literal on-disk v1.2 files reinterpreted as v1.3).
Recorded here so the gap is visible without cross-referencing the run
manifest.
