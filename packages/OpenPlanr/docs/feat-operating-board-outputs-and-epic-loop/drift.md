### 1. Evidence-index.json per-source starvation detail (FR2 / T-003) — schema-blocked, tracked follow-up

FR2's literal text asks for the dot-prefixed/pattern-drop count to be "surfaced as a
warning... **and** in the readable tree... `evidence-index.json` gains per-source
detail." Only the warnings half shipped.

- **Verified independently:** `renderOperatingEvidenceIndex` (`src/services/operate/projection.ts:209-220`)
  is untouched by this spec's diff and still emits only `{id, freshness, status,
  itemCount}` per source (confirmed by reading the function directly — no drop-count
  field exists there).
- **Traced the reason, not just the symptom:** `state.evidenceSources` is populated
  only by the sibling pipeline's `lib/operate/reducer.mjs`, which hard-codes the
  destructure to exactly that field set from `event.payload.sources[]`. That shape is
  itself locked `additionalProperties: false` with the identical fixed field set in
  **both** `schemas/v1.2.0/operating-event.schema.json` and
  `schemas/v1.3.0/operating-event.schema.json` — meaning even T-001's fresh v1.3
  schema work (which this spec's own release touched) still could not have carried an
  extra per-source field at the wire level without widening
  `operating-event.schema.json`, a materially different and larger change than any
  task in this spec was chartered to make.
- **What FR2 delivers instead, with named test coverage:** the loss reaches
  `evidence.warnings` (`operate-evidence-diagnostics.test.ts`,
  `operate-evidence-sources.test.ts`, `operate-evidence-monorepo-fairness.test.ts`), a
  governed `operating-data-gap` opens per starved role
  (`starvedRoleEvidenceGaps`), and `evidence.warnings` is spread into the cycle's
  `warnings` at `engine.ts:1271` — so the loss reaches the cycle record, just not the
  standalone `evidence-index.json` file read in isolation.
- **Status:** ruled a justified, schema-blocked deviation, not a T-003 defect.
  **Genuinely unmet:** an operator reading only `evidence-index.json` (not the cycle's
  warnings, not the gap register) cannot see the starvation count from that file
  alone. Tracked in `qa-report.md`'s Follow-up Register as needing a coordinated
  future pipeline release that widens `operating-event.schema.json`'s
  `evidence.collected` payload (v1.4+ scope) plus a corresponding
  `renderOperatingEvidenceIndex` extension — not achievable inside this spec's
  additive-only v1.3 changes.

### 2. Drifted epic route has no re-election/refresh path (FR8 / T-006 reachability completion) — new in round 2, tracked follow-up

- **Verified independently:** `existingEpicRouteFindingIds`
  (`src/services/operate/routes.ts:552-567`) keys off *any* historical
  `route.proposed` event for the anchor finding — not "successfully applied." If a
  group's `create-epic` route later fails apply with `E_OPERATE_ROUTE_DRIFT` (because
  the group grew after election), that anchor is permanently excluded from
  `electAcceptedFindingEpicRoutes`'s re-election pass, even as the group keeps
  growing.
- **No CLI or action surface compensates:** `src/cli/commands/operate.ts:869-931`'s
  `routes` command group defines exactly two subcommands, `apply` and `rollback` — no
  `refresh`/`re-propose` verb exists.
- **Status:** disclosed by QA's round-2 re-audit as a genuine, non-blocking product
  gap, not a defect in what T-006's round-2 completion was chartered to build (the
  plan amendment's own DoD only asked for reachability + idempotence + R1, all
  delivered). Needs a `routes`-level "refresh" action (or a narrower fix scoping
  `existingEpicRouteFindingIds` to non-drifted/still-live routes) so a grown group can
  be re-elected with its current membership after a drift failure. This is the same
  general "no drift-recovery UX" gap every other route kind already has, but more
  likely to bite in practice for epics, since accepting related findings incrementally
  is an expected operator flow.
- **Related, comment-only inaccuracy (non-blocking, not fixed in this pass):**
  `electAcceptedFindingEpicRoutes`'s own doc-comment (`routes.ts:696-717`) claims a
  grown group "still writes `{A,B,C}`" at apply time; the traced and
  empirically-probed behavior is that apply throws `E_OPERATE_ROUTE_DRIFT` instead.
  The comment describes what `resolveEpicGroupForAnchor` computes, not what the apply
  path does with the resulting digest mismatch. No functional impact — the code is
  correct, only the comment next to it is wrong.
