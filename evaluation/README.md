# Evaluation inputs

This directory contains the inputs consumed by the current skill tests and
commands. Evaluation and conformance code must never be imported by a runtime
package.

- `skills/authoring-cases.json` drives the compiler-backed authoring command tests
  and repair diagnostics.
- `skills/routing-corpus.json` covers positive, negative, ambiguous, alias, and
  collision language. `skills/resilience-journeys.json` covers capability denial,
  host-native question fallback, interruption, and recovery.
- `skills/migrations/` contains the frozen byte comparisons consumed by the
  markdown compiler's compatibility tests.
- `roles/` supplies manual conditional-delegation cases and acceptance criteria;
  its README distinguishes those inputs from executed model evaluations.
- `spikes/diagram-renderer/` retains a runnable renderer benchmark and its recorded
  decision. Its README explains the manual entry point and measured limits.

`npm run skill:evaluate:catalog` evaluates every skill package plus the routing and
resilience checks. `npm run skill:impact` computes affected consumers before a
shared source is edited; see [versioning and impact](../docs/skills/versioning-and-impact.md).

Manual developer tools remain available even when they are not CI gates:
`skill:evaluate:model` explicitly runs a local Codex model evaluation,
`skill:package:check` checks previously generated release archives, and
`skill:benchmark` measures the generated release with optional budget enforcement.
These commands read their documented current inputs; old captured reports are
available through Git history. Model evaluation requires the selected host and
model to be available and is separate from deterministic verification.

Local design evidence under `skills/design-workflow-evidence/` and
`skills/design-workflow-results.{json,md}` stays ignored. Automated tests create
their own temporary fixtures and do not require a contributor's saved runs.

## Claude Code plugin routing suite

`claude-plugin-evals/` is generated by `npm run generate` from the routing-corpus
cases that set `claudePluginEval`; do not edit it by hand. Each case checks that
Claude Code invokes the expected `planr:` skill, does not invoke the case's
`rivalSkillId`, and invokes no other `planr:` skill. Calling the `openplanr` router
is not counted against a positive case, since the router hands off to the expected
skill. A firing rival fails both the rival grader and the other-skill grader, so it
costs a run two of its three points; that extra weight is intended. A negative case
(`"claudePluginEval": {}`) checks that no `planr:` skill fires, the router included.
Graders match a skill called by its namespaced or bare name (`planr:spec` or `spec`).
`npm run check:generated` fails when the suite no longer matches the corpus.

Each run starts in an empty directory. A case can set `claudePluginEval.scaffold`
to a script in `skills/claude-plugin-eval-scaffolds/` that builds a small, offline,
deterministic git repository before Claude starts. `design-loop-variants`,
`design-review-critique`, `investigate-before-ship`, `plan-and-implement`,
`ship-versus-land` and `spec-vague` have one. `ceo-finance`, `plan-review-cross` and
`status-feature` do not, so their prompts can refer to a plan or feature the empty
directory does not hold, and they may score low for that reason rather than
because of routing.

Cases may use `Read`, `Glob`, `Grep` and `Skill`. A case that needs more lists
`Write`, `Edit` or `Bash` in `claudePluginEval.allowedTools`; only
`plan-and-implement` does (`Write` and `Edit`). The CLI grants such tools to every
case in a run, so the runner calls `claude plugin eval` once per tool set, using
the generated `tags`, and the read-only cases never receive them. For the same
reason the runner rejects `--tag`, `--allow-tools` and `--ablation` as extra
arguments.

`npm run skill:evaluate:claude` rebuilds the plugin and runs the suite with the
installed `claude` CLI against `dist/plugins/claude/openplanr`, with a pinned
model, case scaffolds (`--scaffold`), a $10 cost ceiling and no baseline arm
(`--ablation none`): without the plugin no `planr:` skill exists, so a baseline
would only add cost. It is report-only (`--threshold 0`): a low score does not
change the exit code, but a case that fails to load, a run that ends on an API
error, or a cost-ceiling hit still exits non-zero. The ceiling is shared across
the runner's calls; a call that leaves no result stops the run, since its spend
is unknown, and the groups left are named as not run. It calls the model,
so it is a manual check, not a CI gate. Extra arguments pass through, for example
`npm run skill:evaluate:claude -- --runs 1 --case spec-vague`. Results, including
`aggregate-result.json` and `report.html`, go to one folder per tool set under the
ignored `claude-plugin-evals/results/<timestamp>/`, and each run's transcript is
copied to `traces/<case>/<arm>-<n>.jsonl` there; a run whose transcript cannot be copied is
named on stderr. To keep those transcripts the command passes `--keep-temp`, then
removes each run's sandbox from the temporary directory once its transcript is
copied. A sandbox it does not remove is named on stderr; it holds the run's Claude
Code configuration, including the signed-in account's name and email address.
